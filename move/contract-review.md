## 1. 部署物与源码的一致性

先确认评审对象就是链上运行的东西。从测试网 Code Object `0xf7c4b0c7…6d37a` 读取：

| 项 | 链上 | 源码 |
| --- | --- | --- |
| 模块 | `anchor`（唯一） | 一致 |
| 暴露函数 | `submit_batch`，entry，`(&signer, u64, String, vector<u8>, u64)` | 一致 |
| 事件结构 | `BatchAnchored{leaf_schema_version: u64, subject_type: String, merkle_root: vector<u8>, window_end_unix_secs: u64}` | 字段与顺序一致 |
| `upgrade_policy` | `1`（compatible） | `Move.toml` 一致 |
| `upgrade_number` | `1` | 与 2026-09-10 的轮换升级一致 |

**没有多余的公开函数、没有多余的模块、没有任何资源**。攻击面就是这一个函数。

## 2. 函数本体

五条断言，全部在发出事件之前，无状态可写、无算术、无循环、无外部调用：

1. `signer::address_of(caller) == @anchor_signer` —— 编译期绑定的地址。轮换演练已在链上证明它生效：旧账户升级后立即被拒（[rotation-drill.md](./rotation-drill.md)）；
2. `leaf_schema_version > 0`；
3. `subject_type` 属于三个常量之一 —— 逐字节比较，大小写敏感，有单元测试覆盖近似值（`Version`）；
4. `merkle_root` 恰好 32 字节；
5. `window_end_unix_secs > 0`。

**未发现可绕过鉴权的路径。** 无 `friend`、无 `public fun`（除 entry）、无 `init_module`、无 Capability 泄漏——因为根本没有 Capability。没有密钥的攻击者能做的只有让自己的交易 abort 并自付 gas。

## 3. 已接受的风险（第二位评审人请重点复核这三条）

### F1（高）Code Object 可被自由转移，Upgrade Authority 失陷即永久失去升级权

链上 `0x1::object::ObjectCore` 的 `allow_ungated_transfer = true`。也就是说 Upgrade Authority 一旦失陷，攻击者不仅能升级合约，**还能把 Code Object 转走**——此后即使我们仍持有原密钥，也永远无法再升级。

`object_code_deployment` 只在 `ManagingRefs` 里保存 `ExtendRef`，**没有 `TransferRef`**，因此事后无法调用 `disable_ungated_transfer` 关掉这个能力。这不是配置疏忽，是标准部署路径的形态。

补偿控制原本有三层：冷钥离线保管、第 4.9 节的合约变更监控、以及第 4.5 节阶段 E 硬化为 `immutable`。**提案 1.3 版取消了前两层**——不单设 Upgrade Authority（升级权就在环境变量那把签名私钥手上）、也不指定巡检人。因此这条风险目前只剩硬化一条退路，见提案第 0.2 节。

**值得指出的是：硬化为 `immutable` 会同时消灭这条风险**——升级能力没了之后，转走对象也就无所谓了。这是提案第 4.5 节没有写出的一条额外理由，建议补进去。

### F2（中）没有链上停机开关，响应时间受限于取出离线冷钥

合约无状态是刻意的（第 4.5 节「无 Root 之外的可变状态」），代价是**签名密钥被盗时唯一的止血手段是一次升级**——把绑定地址改掉。响应时间因此等于「把 Upgrade Authority 从离线保管中取出并完成一次升级」所需的时间。

轮换演练测得升级本身约 1269 gas units、一次交易即可完成，所以瓶颈完全在人和流程上，不在链上。**建议为这个流程定一个目标时间并写进第 4.6 节**，否则「唯一止血手段」在事故中会是一个没人知道要多久的动作。（1.3 版取消独立冷钥之后，取用不再是瓶颈；但升级权与签名权合一，意味着能触发止血的那把钥匙正是被盗的那把——这条风险改由第 0.2 节承担。）

### F3（中）`compatible` 允许改函数体，因此升级可以改变鉴权行为

`compatible` 只禁止破坏 Struct 布局与 public 签名。轮换演练顺带证实了函数体可改（改的正是那句地址常量）。所以 Upgrade Authority 失陷的攻击者可以发布一个**删掉鉴权断言**的版本，此后任何人都能发出 `BatchAnchored`。

这与提案第 4.6 节的既有结论一致（「Upgrade Authority 泄露只能改变后续合约行为，历史 Event 不受影响」），此处只是把机制确认了一遍：**事件结构布局改不了，历史事件动不了，被污染的只有后续锚定。**

## 4. 建议修改（不阻塞门禁）

**F4（低）`leaf_schema_version` 无上界。** 只校验 `> 0`。一次手误可以把 `10^18` 发上链，链下永远匹配不上，而那条事件无法撤回。加一个上界（例如 `< 1000`）成本为零。**建议在下一次因其他原因升级时顺带修掉**，不值得为它单独发一次升级。

**F5（低）全零 `merkle_root` 会被接受。** 32 个零字节是合法输入。链下不会产生它（空批次被跳过），但合约本身不拦。同上，可顺带加 `merkle_root != [0u8; 32]`。

## 5. 供 Verifier 作者参考的两点

**`window_end_unix_secs` 是调用方自报的，不是时间证明。** 合约不与链上时钟比对。任何关于「什么时候」的断言必须用交易自身的时间戳；第 4.8 节的 SLO 建立在自报值上，因此是**内部指标，不可外部验证**——这一点应当在对外表述中说清楚。

**`0x1::code::PackageRegistry` 的 `upgrade_number` 是一个独立的交叉校验点。** 它由链维护、任何人可从公共节点读取，与 re0 的监控无关。Verifier 可以用它独立确认这个包被升级过几次，从而判断历史签名地址集合（第 4.5 节）是否完整。

## 6. 结论

在密钥不失陷的前提下，**合约本身未发现可被利用的缺陷**。全部三条中高风险都源于「保留升级能力 + 单一离线密钥」这一组已在第 0 节决策的取舍，而非实现错误。

门禁 3 尚未满足：**需要第二位评审人**。建议其重点为第 3 节，特别是 F1 与提案第 0.2 节——1.3 版豁免门禁 2、4、8 之后，F1 的补偿控制只剩硬化为 `immutable` 一条。
